# 1. 멀티 스레드 컨슈머 애플리케이션
![[Pasted image 20260720112146.png|594]]
처리량을 늘리려면 파티션과 컨슈머를 함께 늘려야함. 데이터 병렬처리를 위해 파티션 개수와 컨슈머 개수를 동일하게 맞추는 것이 가장 좋은 방법. 
운영 형태는 둘 다 가능:
- n개 스레드를 가진 1개 프로세스 (스레드로 확장)
- 1개 스레드를 가진 n개 프로세스 (프로세스로 확장)
	- `@KafkaListener`의 `concurrency` 설정


# 2. 컨슈머 랙
![[Pasted image 20260720112501.png|582]]
컨슈머 랙 = 파티션의 최신 오프셋(LOG-END-OFFSET) − 컨슈머 오프셋(CURRENT-OFFSET) = 아직 처리 못 한 레코드 수
- 프로듀서 전송량 > 컨슈머 처리량 → 랙 증가. 반대면 랙 감소, 최솟값 0(지연 없음)
- 컨슈머 그룹 × 토픽 × 파티션별로 생성됨.
	- ex) 파티션 3개짜리 토픽을 1개 그룹이 구독하면 랙은 총 3개

### 확인해야 하는 이유
1) 컨슈머 장애 확인
	ex) 프로듀서는 그대론데 특정 파티션 랙만 치솟으면 → 그 파티션 담당 컨슈머에 이슈
2) 파티션 개수 산정 참고 
	ex) 사용량 폭증처럼 전송량이 튀면 랙 발생 → 일시적으로 파티션·컨슈머를 늘려 병렬처리량 확장으로 대응


# 3. 컨슈머 랙 모니터링 방법

| 방법                                    | 장점                                                                | 한계                                                                     |
| ------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `kafka-consumer-groups.sh --describe` | 가장 기초적                                                            | 일회성: 지속 기록·모니터링엔 부족. 테스트용 카프카에서 주로                                     |
| 컨슈머 앱에서 `metrics()` 메서드               | 코드로 지표 확인 (`records-lag-max` `records-lag` `records-lag-avg` 3가지) | 컨슈머가 정상일 때만 확인 가능(비정상 종료 = 모니터링 불가) · 모든 컨슈머 앱마다 중복 코드 · 서드파티 앱은 측정 불가 |
| 외부 모니터링 툴                             | 가장 최선의 방법. 클러스터 단위 종합 모니터링 + 컨슈머 동작에 영향 없음                        | 별도 구축 필요                                                               |
종합 모니터링 툴: 데이터독(Datadog), 컨플루언트 컨트롤 센터
랙 전용 오픈소스: 버로우(Burrow)
