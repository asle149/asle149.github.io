# 1. 프로듀서 소개
프로듀서(Producer) = 카프카에서 데이터가 태어나는 곳. 필요한 데이터를 만들어(선언하여) 브로커의 특정 토픽 파티션으로 전송하는 애플리케이션

![[Pasted image 20260708221609.png]]

```mermaid
graph LR
    PR["ProducerRecord<br/>(토픽·파티션·타임스탬프<br/>·메시지 키·값)"] -->|"send()"| PT[Partitioner<br/>어느 파티션으로?]
    PT --> ACC["Accumulator<br/>배치로 모으는 버퍼<br/>(토픽A: 배치0·배치1 …)"]
    ACC --> SND[Sender<br/>배치를 가져가<br/>브로커로 전송]
    SND --> K["🐘 카프카<br/>클러스터"]
```

| 구성 요소          | 역할                                           |
| -------------- | -------------------------------------------- |
| ProducerRecord | 프로듀서가 생성하는 레코드. 오프셋은 미포함(오프셋은 브로커에 저장될 때 붙음) |
| send()         | 레코드 전송 요청 메서드 (바로 전송이 아니라 "요청"!)             |
| Partitioner    | 어느 파티션으로 보낼지 결정. 기본값 DefaultPartitioner      |
| Accumulator    | 배치로 묶어 전송할 데이터를 모으는 버퍼                       |
| Sender         | 어큐뮬레이터에 쌓인 배치를 가져가 실제로 브로커에 전송하는 스레드         |

# 2. 프로듀서 파티셔너
### 1) 기본 파티셔너

|       | RoundRobinPartitioner                | **UniformStickyPartitioner** (기본)  |
| ----- | ------------------------------------ | ---------------------------------- |
| 동작    | ProducerRecord가 들어오는 대로 파티션을 순회하며 전송 | 어큐뮬레이터에서 레코드들이 배치로 묶일 때까지 기다렸다가 전송 |
| 배치 효율 | 묶이는 정도가 적음                           | 배치 단위로 꽉 채워 보냄                     |
| 성능    | 낮음                                   | RR의 단점을 개선 → 향상된 성능                |
| 분배    | 파티션 순회                               | 배치로 묶일 뿐 결국 파티션을 순회 → 모든 파티션에 분배됨  |

### 2) 커스텀 파티셔너
특정 데이터를 특정 파티션에 고정하고 싶다면 `Partitioner` 인터페이스를 구현


# 3. 프로듀서 주요 옵션
### 1) 필수 옵션
| 옵션                  | 뜻                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------- |
| `bootstrap.servers` | 데이터를 전송할 대상 클러스터의 **브로커 호스트:포트, 1개 이상**. **2개 이상 넣으면** 일부 브로커에 이슈가 생겨도 접속에 문제없게 할 수 있음  |
| `key.serializer`    | 메시지 **키를 직렬화**하는 클래스                                                                    |
| `value.serializer`  | 메시지 **값을 직렬화**하는 클래스                                                                    |

### 2) 선택 옵션

| 옵션                                      | 기본값                | 뜻                                                     |
| --------------------------------------- | ------------------ | ----------------------------------------------------- |
| `acks`                                  | 1              | 전송한 데이터가 브로커에 정상 저장됐는지 확인하는 수준 (0 / 1 / -1(all))      |
| `linger.ms`                             | 0                  | 배치를 전송하기 전까지 기다리는 최소 시간                               |
| `retries`                               | 2147483647         | 브로커에서 에러를 받은 뒤 재전송 시도 횟수                              |
| `max.in.flight.requests.per.connection` | 5                  | 한 번에 요청하는 최대 커넥션 개수(동시 전달 요청 수)                       |
| `partitioner.class`                     | DefaultPartitioner | 파티셔너 클래스 지정                                           |
| `enable.idempotence`                    | true               | 멱등성 프로듀서(같은 데이터를 여러 번 보내도 브로커에 중복 적재되지 않게 하는 것)로 동작할지 |
| `transactional.id`                      | null               | 레코드를 트랜잭션 단위로 묶을지                                     |


# 4. ISR과 acks 옵션
ISR = 리더 파티션과 팔로워 파티션이 모두 싱크(동기화)가 된 상태(묶음)
acks = 어디까지 저장 확인하고 성공으로 칠까
	0, 1, all(-1) 값 가질 수 있음

#### 1) acks=0: 보내기만 하고 확인 안 함
![[Pasted image 20260708223358.png]]
- 프로듀서가 리더 파티션으로 데이터를 전송한 뒤, 저장됐는지 확인하지 않음. (원래 리더는 "몇 번째 오프셋에 저장됐다"를 리턴해주는데, 그 응답값을 안 받음)
- 가장 빠름. 대신 유실돼도 모름.
- 용도: 일부 유실을 감수하더라도 속도가 중요한 데이터 (예: GPS 위치처럼 계속 쏟아지는 로그).

#### 2) acks=1 (기본값): 리더까지만 확인
![[Pasted image 20260708223501.png]]
- 보낸 데이터가 리더 파티션에만 정상 적재됐는지 확인. 적재 안 됐으면 될 때까지 재시도 가능.
- 그래도 유실될 수 있다! 리더 적재를 보장해도, 팔로워가 복제하기 직전에 리더 브로커가 장애나면 동기화 못 한 데이터가 사라짐.

#### 3) acks=all(-1): 리더 + 팔로워까지 확인
![[Pasted image 20260708223543.png]]
- 리더뿐 아니라 팔로워 파티션까지 적재됐는지 확인. 0·1보다 느리지만, 일부 브로커 장애에도 안전하게 전송·저장 보장.
- all의 실제 기준은 `min.insync.replicas`  "ISR 중 최소 몇 개 파티션에 적재를 확인할까"의 값.

#### 4) min.insync.replicas: all의 몇 개까지?
![[Pasted image 20260708223635.png]]
ISR의 2개 이상 파티션(최소한 리더 + 팔로워 1개)에 적재를 확인
실제 운영에서 브로커 2대가 동시에 죽는 일은 극히 드물기 때문

`min.insync.replicas` > 복제 개수 = 전송 불가!
